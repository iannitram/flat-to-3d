# 007 First Light: route to true stereo for 1.0

Researched 2026-11-11 on the handheld (SteamOS). Web sources plus a read-only look at the installed copy: the game was not launched and nothing in the game folder or the Proton prefix was changed. This note builds on [games_group_a.md](../games_group_a.md) ("007 First Light") and does not repeat it; where the two disagree, this note is newer and says why.

Each finding is marked **observed** (seen in the installed files or on the linked page) or **inferred** (a conclusion drawn from what was observed). Addresses are RVAs (image base `0x140000000`) and hold only for the build named in section 2.

**Short answer.** The game is safe to modify (no Denuvo, no anti-cheat, single-player). The OpenVR lead from the first research pass is dead: the exe never loads the `openvr_api.dll` that ships beside it. What the exe does still hold is Glacier's **dummy VR device**, built at start-up on every run, with a `stereo3d` rendering mode and an eye distance. The recommended route is a small DLL of our own that switches that device on and shows its two eye views side by side. No existing free tool gives this game two real camera views.

## 2. Installed copy (static inspection)

The game is installed on the handheld's internal Steam library. Build inspected: Steam build `26430236`, updated 2026-11-06; `007FirstLight.exe` is 65,055,112 bytes, link date 2026-11-04, SHA-256 starting `f92c0e8600aa3b69`. The prefix last ran on Proton Experimental (11.0-100).

**Layout (observed)**

- `Retail/`: the exe, its DLLs, `thumbs.dat` (the engine's config) and `PipelineCache.bin`.
- `Runtime/`: `chunk0.rpkg` and `chunk1.rpkg` (53 GB together) and `packagedefinition.txt`.
- No PDB ships. C++ type names (RTTI) are kept, for example `.?AVZRenderVRDeviceDummy@@`, and source paths and function names appear in profiler strings (`ZRenderVRDeviceBase::RenderMirrorTexture`). That is enough to find classes and many functions without symbols.
- Upscalers and frame generation: DLSS super resolution, ray reconstruction and frame generation through Streamline (`nvngx_dlss.dll`, `nvngx_dlssd.dll`, `nvngx_dlssg.dll`, `sl.*.dll`); FSR upscaler and frame generation (`amd_fidelityfx_upscaler_dx12.dll`, `amd_fidelityfx_framegeneration_dx12.dll`). The exe names XeSS but no XeSS DLL ships. Path tracing is a setting (`RTPathTracingMode`).

**Config (observed)**

- `thumbs.dat` and `packagedefinition.txt` are XTEA-encrypted text. The key Hitman used does not open them; the 007 key published in [rpkg-rs](https://github.com/dafitius/rpkg-rs/blob/main/src/encryption/xtea.rs) (Apache-2.0) does, and the checksum matches. It was decoded in memory only.
- `thumbs.dat` is a Glacier ini: an `[application]` section with `KEY=value` options (`SCENE_FILE`, `NO_RESOURCEDB=1`, `OnlineDisableAutoReconnect=1`) and `ConsoleCmd <name> <value>` lines (one is present: `ConsoleCmd Render_ShowDebug 0`). It holds no VR or stereo key.
- The exe also names `user.ini`, `!include` and `-IgnoreUnversionedIni`, so an extra ini file may be read without touching `thumbs.dat`. Whether the retail build honours it is not known.
- Player settings are in the prefix registry under `Software\IO Interactive\007 First Light` (50 values: resolution, upscalers, quality). None is a VR or stereo setting. `VRSProfile` there is variable rate shading, not VR.

**Stereo and VR code compiled in (observed)**

| Thing | Where | What it shows |
|---|---|---|
| `ZRenderVRDeviceBase`, `ZRenderVRDeviceDummy`, `IRenderVRDevice`, `IRenderVRSwapChain` | RTTI names | A VR render device layer is in the exe. `ZRenderVRDeviceDummy` is the only device class: its base constructor (`0xed4d10`) has one caller |
| `ZRenderVRDeviceDummy` constructor | `0xed9060`, vtable `0x2dce588` | Reads the application option `VRDeviceTypeOverride` as a number and picks one of three size presets (unset, 0, 1) |
| The one call to that constructor | `0xe65df0`, in the render device start-up beside the `RenderThread` set-up | It is not behind any option: the dummy device is built on every run and stored at render device `+0x17cc0`, with the byte at device `+0x780` set to 0 |
| `off`, `cinema`, `stereo3d` and the log line `[{0}] mode {1} - res {2} - ipd {3} - wno {4}` | string use at `0xed6296` | The device has a mode and an eye distance (IPD) |
| `ZRenderVRDeviceBase::ResolveVirtualBackbuffer`, `ZRenderVRDeviceBase::RenderMirrorTexture`, `- virt {0}x{1}x{2}` | profiler strings | The device owns a virtual backbuffer and draws a mirror picture to the window |
| `VRDummyInputControl={VRDummyKBMMousePosX= rel(ms,x); ...}` | string | The dummy device takes head turning from the mouse (hold mouse button 4) |
| `ZVRCameraEntity` (`EEye`: `eLeftEye`, `eRightEye`), `ZVRManager`, `ZVRGlobalEntity`, `ZVRFlowManagerEntity`, `ZVRTrackedSpatialEntity`, `LightTileVR` | RTTI and strings | Game-side VR entities and a VR variant of the light tiling are still compiled |
| `$vrmode`, `$isvrdeviceactive`, `$isvrdeviceavailable`, `SetVrModeActive`, `vr_quality`, `vr_StepVRCamera` | strings | The menu system and settings still know a VR mode |

The community type dump for this game gives the enum values behind those names ([ZHMTools, KNT enums](https://github.com/OrfeasZ/ZHMTools/blob/master/Libraries/ResourceLib/Src/Generated/KNT/ZHMEnums.cpp), LGPL-3.0):

- `EVRRenderingMode`: `VR_RENDER_MODE_2D_SCREEN` = 0, `VR_RENDER_MODE_STEREO_3D` = 1.
- `EVRRenderDeviceType`: `RENDER_VR_DEVICE_TYPE_DUMMY` = 0, `_OCULUS` = 1, `_PSVR` = 2, `_OPENVR` = 3.
- `ERenderVRTrackingID`: head 16, left eye 17, right eye 18, left hand 19, right hand 20.

**What is not there (observed)**

- The exe does not import `openvr_api.dll`, has no delay-import table, and does not contain the text `openvr_api` in ASCII or UTF-16. It has no OpenVR interface names (`IVRSystem`, `IVRCompositor`, `VR_Init`), no Oculus runtime loader and no OpenXR loader. No other shipped DLL names `openvr_api.dll`.
- `openvr_api.dll` (819,664 bytes, built 2020-09-16) is a leftover file. `openvr` and `oculusvr` appear in the exe only in a list of controller types.
- The `UI_OPTION_DISPLAY_STEREOSCOPIC`, `_STEREO_DEPTH` and `_STEREO_STRENGTH` names are menu label ids in an enum (2310, 2320, 2330 in the type dump). No setting, registry value or console command with a matching name exists.

**Inferences**

- `VR_RENDER_MODE_2D_SCREEN` is logged as `cinema` and `VR_RENDER_MODE_STEREO_3D` as `stereo3d`; `off` is the device when not active.
- The byte at device `+0x780` is the "active" flag (the constructor and the creator both clear it; a one-line getter at `0xed9260` returns it).
- The dummy device is a developer tool for testing VR rendering without a headset. That is exactly the shape this project wants: two engine-drawn eye views, a fixed head, a picture in the game window.
- This corrects [games_group_a.md](../games_group_a.md) and test 7 in [research-report.md](../../research-report.md): starting SteamVR with VRto3D cannot wake a VR mode, because no code in the game talks to OpenVR. The "Stereoscopic" menu option is a label without a setting behind it, not a second lead.

## 4. Recommended route and fallback

### Recommended: switch on the dummy VR device (`stereo3d`) and show it side by side

A DLL of our own, loaded with the game, turns the engine's dormant stereo on. The engine then draws both eyes itself, so shadows, lighting and the HUD come from the game's own VR path and not from a second pass we bolt on.

Hook points, in the order the work would go:

1. **Load.** A `dinput8.dll` proxy in `Retail/` with `WINEDLLOVERRIDES=dinput8=n,b` set by `flat3d-run`, the way ZKntSDK loads. The engine installs and removes the file; nothing else in the game folder changes.
2. **Find the device.** Locate `ZRenderVRDeviceDummy` by its RTTI name, take its vtable, and read the object pointer the render device keeps (`+0x17cc0` on this build). Finding by RTTI name and by pattern, not by fixed address, is what keeps the recipe alive across game patches.
3. **Activate it.** Call the device's own activate and set-mode methods (to be mapped from the vtable at `0x2dce588`; the `off` / `cinema` / `stereo3d` log function at `0xed6296` is the quickest way to learn which fields hold the state). Set the mode to `VR_RENDER_MODE_STEREO_3D` and the IPD to the recipe's value. Writing the flag at `+0x780` directly is the crude first probe, not the final method.
4. **Keep the game-side VR flow quiet.** `ZVRManager`, `ZVRFlowManagerEntity` and the `$vrmode` menu binding may react (a VR set-up screen, the VR HUD, first-person VR camera entities). The aim is "render device in stereo, game logic flat". If the game logic insists on following, pin `$vrmode` and `ZIsVRActive` to false while the render device stays active.
5. **Fix the head.** Leave the dummy tracking at its rest pose and block `VRDummyKBMMouseActivateRotation`, so the picture is a fixed 3D TV (ruling 4).
6. **Get a side-by-side picture.** If `RenderMirrorTexture` already draws both eyes to the window, nothing more is needed. If it draws one eye, copy the two eye images from the device's virtual backbuffer into the left and right halves of the swap chain image before present. The SBS viewer then treats the game like a Geo-11 game.
7. **Settings.** Frame generation off (DLSS and FSR), path tracing off, fullscreen at a 32:9 or half-width SBS size, FSR upscaling at Performance to hold 30 fps.

Risks:

- **The stereo path may be rotten.** The device code is compiled, but nobody has shipped it on this renderer (frame graph, path tracing, new upscalers). It may crash, draw one eye, or skip passes. This is the biggest risk and only a launch can settle it.
- **The game data may lack VR content.** Hitman's VR used VR-specific camera and hand entities in the scene data. If the eye cameras come from `ZVRCameraEntity` instances that the 007 scenes do not contain, the device may be active with nothing driving the eyes. Then our DLL has to feed the two eye transforms itself (camera position plus and minus half the IPD), still using the engine's two-eye render.
- **Performance.** Two eyes on a game that is already CPU-bound in crowds ([games_group_a.md](../games_group_a.md)). 30 fps is plausible, not shown.
- **Patches.** The exe changes with every game update (the last was 2026-11-06). Pattern-based lookup limits the damage; a recipe should still record the build it was checked on.
- **Online.** A modified client would be talking to IOI's servers unless the route forces offline mode. See the open questions.

### Fallback: our own two-pass DX12 stereo (issue #11)

If the dummy device cannot be made to draw two eyes: hook the camera data the renderer consumes (`SRenderCameraData`, reachable through the same hooks ZKntSDK uses) and render each eye in turn, shifting the camera by half the IPD and the projection by the matching offset, then pack the two results side by side. Rendering both eyes inside one frame doubles the CPU cost and needs every temporal effect (TAA, upscaler history, motion vectors) kept per eye. Alternating eyes per frame is cheaper but is alternate-eye rendering, which ruling 3 has not accepted. This is a large reverse-engineering job and would not fit a 1.0 timeline on its own.

There is no third route. Without one of these two the game stays flat in 1.0.

## 6. Tests still needed and proposed issues

On-device tests, cheapest first. Tests 1 to 3 need no code of ours.

1. Start the game once with the network off and load a save. Confirms offline play.
2. Start the game flat with `PROTON_LOG=1` and search the log for the `[VR] Dummy device` and `mode ... ipd ...` lines. Confirms the device is created under Proton and shows its default mode.
3. Add `VRDeviceTypeOverride=1` through a `user.ini` (or, failing that, a re-encrypted copy of `thumbs.dat`, with the original kept) and repeat test 2. Shows whether retail builds read extra options, and what the override changes.
4. Build ZKntSDK from source and check that its menu opens under Proton on the current game build. Proves the loader and the pattern lookups.
5. With a probe mod: read the dummy device object, print its state, then set it active with mode `stereo3d` in the main menu. Record what the window shows (crash, one eye, two eyes, VR set-up screen).
6. Repeat test 5 inside a mission; capture a frame; measure the pixel offset between the eyes for a far object and for the HUD.
7. Measure the frame rate in a crowd scene at FSR Performance with stereo on.
8. Put the side-by-side picture through the SBS viewer on the headset over WiVRn and check depth on the fixed screen.

## 7. Open questions for the owner

1. **Order.** The three new 1.0 games have no order yet. This note assumes 007 First Light comes after the four existing games. Is that right, and where does it sit against Alan Wake 2 and Forza Horizon 6?
2. **Online.** The game is single-player with no anti-cheat, but it connects to IOI's servers when it can. Should the 3D route always force offline mode, so a modified client never talks to those servers?
3. **Scope.** This route is a build of our own with a real chance of failing at test 5. If it fails, is 007 First Light allowed to drop out of 1.0, or does the two-pass fallback (large) stay in 1.0?
4. **Alternate-eye rendering.** Still not ruled (ruling 3). It decides whether the cheaper form of the fallback is allowed.
5. **ZKntSDK.** Build on it (GPL-3.0, same licence as this repo, extra dependency that can lag behind game patches) or write a smaller loader of our own inside the engine and use ZKntSDK only as a reference?
6. **Game updates.** Should Steam auto-update be held for this game once a recipe works, since each patch can break the lookups?
