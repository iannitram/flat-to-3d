# True stereo 3D on SteamOS: Control, Alan Wake 2, Marvel's Spider-Man 2, Hades, Hades II

Research date: 2026-10-18. Render machine: ROG Flow Z13 (Radeon 8060S, RDNA 3.5 iGPU), SteamOS, Proton. "Local" citations are read-only inspections of the install folders listed in `library-scan.tsv`, plus my per-game notes in `my per-game notes`.

Three terms come up throughout:
- **Geometry-level stereo (3DMigoto / geo-11):** a d3d11 wrapper that draws every draw call twice with per-eye shader corrections. Both eyes come from the same frame, at the same moment. DX11 only.
- **AER (Alternate Eye Rendering):** used by R.E.A.L. VR and by the modder's "NoMoreFlat" mods. It is still true two-camera stereo, but only one eye is rendered per engine tick and the other eye is reprojected from its previous image. Each eye gets half the game's frame rate, and you see ghosting or "eye-flip" artifacts when the frame rate drops or the camera pans sideways.
- **VRto3D:** an OpenVR/SteamVR driver (oneup03) that takes a VR mod's two eye images and outputs them as a flat SBS/TAB 3D screen. It is the established community bridge from a "VR mod" to a "3D TV", which is exactly our use case. It has a native Linux SteamVR build.

## Control Ultimate Edition (Northlight, DX11/DX12): Geo-11 / 3D fix? the R.E.A.L. VR author? Free VR mod?

### Takeaway
A free, true-stereo route exists today: Losti's 3D-Vision-Ready fix (a 3DMigoto fix, DX11 only) running on bo3b's geo-11 driver, which works on AMD, outputs SBS/TAB, and is reported to work under Proton. Control is not in R.E.A.L. VR's free R.E.A.L. VR list, and I found no free VR mod for it. **Verdict: likely with work.** Every piece exists; it has not been tested on Proton + 8060S, and the HelixSR/OptiScaler test files currently in the game folder have to come out first.

### Cited Findings
- Engine: Remedy Northlight; Direct3D 11 and 12, chosen through the launcher or with command-line arguments — [PCGamingWiki: Control](https://www.pcgamingwiki.com/wiki/Control)
- PCGamingWiki rates NVIDIA 3D Vision as "hackable" and points to the Helix Mod fix by Losti. vorpX officially supports Control (G3D/Z3D modes), but vorpX is paid — [PCGamingWiki: Control](https://www.pcgamingwiki.com/wiki/Control)
- Losti's fix (V1.01, 2019-11-30; Masterotaku co-credit) is built on 3DMigoto. It is **DX11 only** ("Ray Tracing and DLSS may not supported"), and commenters report 3D does not work in DX12. Known issues: some AO shadows wrong, SSR not fully correct, global reflections can cause discomfort (turn them off), HUD depth glitches, enemy marker glitches. Download: `losti.s3.amazonaws.com/Control_3D-VisionReadyFix_1.01_by_Losti_Masterotaku.zip`. A commenter says Masterotaku later released an updated version (not linked) — [Helix Mod blog: Control 3D-Vision-Ready fix](https://helixmod.blogspot.com/2019/10/control-3d-vision-ready-fix-losti-v100.html)
- Comments on that page (unverified, mixed): in 2025 users report the fix working with **geo-11**, including on the Epic version after editing the output setting. One AMD + RTX 40 user saw broken shadows on the Steam version and correct results on Epic, and advises avoiding F10 and using borderless fullscreen — [Helix Mod blog: Control fix comments](https://helixmod.blogspot.com/2019/10/control-3d-vision-ready-fix-losti-v100.html)
- geo-11 is built on 3DMigoto. It has no DX12 support and no plans for it. It "has been shown to run on AMD cards". Outputs include SBS, TAB, interlaced, checkerboard and anaglyph, plus katanga_vr for headsets. The announcement states "Linux with Proton also works" — [Helix Mod blog: Announcing geo-11](https://helixmod.blogspot.com/2022/06/announcing-new-geo-11-3d-driver.html)
- R.E.A.L. VR's free public list (38 games, March 2026) does not include Control — [DTF: R.E.A.L. VR made free](https://dtf.ru/games/4836883-luke-ross-real-vr-framework-besplatno)
- Anti-cheat / online: Control is DRM-free on Epic and GOG — [PCGamingWiki: Control](https://www.pcgamingwiki.com/wiki/Control). It is not in the AreWeAntiCheatYet database, which lists 1,167 games with anti-cheat (local check of [AreWeAntiCheatYet games.json](https://github.com/AreWeAntiCheatYet/AreWeAntiCheatYet)). It is a single-player game.
- Local: the install has `Control_DX11.exe` / `Control_DX12.exe`. Since 2026-10-17 the folder also holds a **HelixSR Scaler test**: `dxgi.dll` (26 MB, an OptiScaler-based proxy), plus `HelixSR/`, `OptiScaler.ini` and the removal script `HelixSR-Scaler-remove.sh`. My notes say the normal setup is DX11 with `-dx11`, Proton 11.0, 1920×1200, and lsfg 3× from a 60 base — local `<Steam library>/steamapps/common/Control/`; `my per-game notesControl Ultimate Edition.md`

### Inferences
- Route: run `-dx11`, then 3DMigoto/geo-11 `d3d11.dll` + Losti's ShaderFixes, with the output set to SBS (full or half). Under Proton the game's own d3d11.dll must be overridden (`WINEDLLOVERRIDES="d3d11=n,b"`) so 3DMigoto loads ahead of DXVK. The SBS window is then shown as a fixed 3D screen in the Quest. This gives synchronous true stereo, which is better than AER, and needs no SteamVR.
- The HelixSR `dxgi.dll` proxy should be removed, using its own script, before 3DMigoto is tested. Two DXGI/D3D proxies in one folder is a known source of conflicts, and the fix targets DX11 while HelixSR targets DX12.
- Performance: geometry stereo roughly doubles draw/vertex work, and pixel work at full-width SBS. The Z13 currently runs a 60 fps base in DX11 at 1200p before frame gen. Expect roughly 30–40 fps in stereo at 1200p, more at a lower render resolution. That meets the 30 fps floor. lsfg-vk frame gen on an SBS frame is untested and may break eye consistency. Treat it as off.
- Since the 2019 fix, game patches (for example the 2020 Ultimate Edition update) may have changed shader hashes. The comments suggest the fix mostly still works, but that needs a hands-on check.

### Gaps
- No first-hand report of geo-11 + Control on Proton/SteamOS specifically. The geo-11 page's Proton claim is generic.
- I could not find the "Masterotaku updated version", or whether a geo-11-specific Control profile exists (the 3DJ database was not checked).
- Free Control VR mod: none found (searched Flat2VR, GitHub). Absence is not proof.

## Alan Wake 2 (Northlight, DX12 only, mesh shaders): any stereo approach? the R.E.A.L. VR author?

### Takeaway

### Inferences
- Route: NoMoreFlat (OpenXR) in the game under Proton → an OpenXR runtime that hands frames to SteamVR → the VRto3D driver set to SBS → that SBS window on the Quest's fixed virtual 3D TV. The open question is how the Windows OpenXR loader inside Proton reaches Linux SteamVR. SteamVR for Linux has a Proton OpenXR/OpenVR bridge, but that is unverified for this mod. A simpler variant: send the mod straight to the Quest with head tracking frozen, if the mod offers an option to disable it.
- Performance: AER keeps the engine at mono cost (a small reprojection overhead), so the game still runs about 55–60 fps. But each eye refreshes at half that, about 28 fps, and the guide warns that frame drops cause eye-flips. That just meets the 30 fps-per-eye floor, with no headroom. Lowering FSR to Performance bought only ~2 fps per the wiki, so there is little room to gain. Expect a marginal experience.
- If the AW2 build stays Patreon-only, it counts as **paid** under the free-only rule. Then the route is "build our own": a REFramework-style D3D12 hook (the modder's MIT code as a template) that finds Northlight's camera/view matrix, offsets it per eye and renders AER or two passes. A synchronous two-pass render in AW2 would double a GPU cost that is already at its limit, so AER is the only realistic option on an 8060S.

## Hades and Hades II: rendering model and verdict

### Takeaway
**Hades (1) is truly 2D for stereo purposes:** characters are pre-rendered 3D animation baked into sprite frames, painted 2D environments, an orthographic-style fixed camera. **Won't work.** **Hades II is a hybrid:** environments are still 2D art, but the install ships Granny 3D character models (`.gpk`) and `Granny3D` / `Lighting3D` shaders, matching marketing that describes "real-time 3D characters". True two-camera stereo would add depth only to characters against flat painted layers under a fixed top-down camera. **Won't work (keep the ruling).** It is technically not pure 2D, but there is no real 3D world to separate.

### Cited Findings
- Hades engine: MonoGame in early access, then a new C/C++ engine built with ConfettiFX's **The Forge** at release; Direct3D 11 plus a Vulkan 1.1 build (October 2020); fixed 1920×1080 internal viewport — [PCGamingWiki: Hades](https://www.pcgamingwiki.com/wiki/Hades); [The Forge on GitHub](https://github.com/ConfettiFX/The-Forge#supergiant-games-hades)
- A Supergiant developer reply (2019): Hades does not use real-time 3D rendering; characters were 3D-rendered and animated, then output as thousands of pre-rendered frames from many angles — [Steam: Hades discussion](https://steamcommunity.com/app/1145360/discussions/0/1738883810796606862)
- Hades II: The Forge; Direct3D 12; fixed 1920×1080 internal viewport — [PCGamingWiki: Hades II](https://www.pcgamingwiki.com/wiki/Hades_II). Store/marketing copy describes "even smoother real-time 3D characters" — [Epic Games Store: Hades II](https://store.epicgames.com/en-us/p/hades-ii)
- Local evidence: Hades II ships `Ship/granny2_x64.dll`, `Content/GR2/_Optimized/` with 290 files (`.gpk`/`.sdb` pairs named per character, e.g. `Apollo.gpk`, `Arachne.gpk`), and D3D12 shaders `Granny3D.shader`, `Granny3DSprite.shader`, `Default3D.vert`, `Lighting3DFast.*`, `Blit2DDepth.*`, alongside many `*2D` blend shaders. Hades 1 has no GR2 folder; its `Content/Win/EffectsForgeD3D11` has mostly 2D blend shaders plus a `Lighting3D` and `ShadowMap` pair (probably sprite lighting) — local `<Steam library>/steamapps/common/Hades II/`, `<Steam library>/steamapps/common/Hades/`
- Neither game lists anti-cheat (both DRM-free when launched directly) — [PCGamingWiki: Hades](https://www.pcgamingwiki.com/wiki/Hades); [PCGamingWiki: Hades II](https://www.pcgamingwiki.com/wiki/Hades_II)
- No stereo/VR mods found for either game (PCGamingWiki has no VR-support entries for them).

### Inferences
- Hades II's 3D characters are probably drawn with an orthographic projection into a 2D-composited scene, possibly with depth (`Blit2DDepth`). A per-eye horizontal shear of that projection could give characters real relief and put them in front of a flat background, but the floor, walls and props are painted 2D layers with no per-pixel depth. The result would be "cardboard cutout" stereo at best. That does not justify a custom DX12 build, so the "won't work" ruling stands for both. If I ever wants a curiosity: Hades (1) DX11 → 3DMigoto could put sprite layers at hand-assigned depths (a "layer-depth" fix, as some 2D games got on Helix), but that is not two cameras.

### Gaps
- No Supergiant technical statement on how Hades II composites its 3D characters (orthographic camera, depth buffer use). This is inferred from file names only.

## "Build our own" stereo for Northlight and the Insomniac engine: what it would involve

### Takeaway
Under Proton, the practical place to build is **inside the Windows process** (a D3D11/D3D12 proxy DLL or a REFramework/ReShade-style hook), not in DXVK/vkd3d-proton. Existing free code shows the pattern: the modder's MIT-licensed starfield2vr/anvilengine2vr (D3D12 + OpenXR via a DXGI hook) and 3DMigoto/geo-11 (D3D11, per-draw stereo). Doing it at the vkd3d layer is possible in principle but much harder, because the translation layer only sees Vulkan pipelines and descriptor buffers, not "the camera".

### Cited Findings
- the modder's mods: `starfield2vr` is "based on PrayDog's REFramework" with OpenXR/OpenVR builds and 6DoF; `anvilengine2vr` uses "DXGI hooking by default – the `dxgi.dll` file should be placed in the game root", OpenXR runtime, MIT license. Known limitation: some effects are invisible when looking the opposite way (screen-space culling) — [starfield2vr](https://github.com/mutars/starfield2vr); [anvilengine2vr](https://github.com/mutars/anvilengine2vr)
- The Helix Mod AW2 thread says synchronized (both-eye-per-frame) rendering is "very hard without access to the game's source code", which is why NoMoreFlat uses AER — [Helix Mod: Alan Wake 2 NoMoreFlat](https://helixmod.blogspot.com/2025/04/alan-wake-2-nomoreflat-vrto3d.html)
- geo-11 has no DX12 support ("DX12 is a completely different ballgame") — [Helix Mod: geo-11](https://helixmod.blogspot.com/2022/06/announcing-new-geo-11-3d-driver.html)
- AER: one eye is rendered per tick and the other reprojected — [the R.E.A.L. VR author Patreon](https://www.patreon.com/posts/lets-do-space-74012973). The newer MGS2-PCVR project added an experimental "Two Eye" mode where both eyes get a fresh frame each game frame — [MGS2-PCVR v0.5.0](https://newreleases.io/project/github/Shiffo0/MGS2-PCVR/release/v0.5.0)
- Local: Control ships both Win7 (DX11) and Win10 (DX12) renderer DLL sets (`d3d_rmdwin7_f.dll`, `d3d_rmdwin10_f.dll`, etc.). Alan Wake 2 is a single `AlanWake2.exe` with `D3D12Core.dll` (Agility SDK). Spider-Man 2 is a single `Spider-Man2.exe`, D3D12 with DirectStorage — local install folders.

### Inferences
- **Steps for a DIY AER stereo mod (either engine):** (1) Inject: put a `dxgi.dll`/`d3d12.dll` proxy in the game folder, loaded under Proton with `WINEDLLOVERRIDES`. (2) Find the camera: use a RenderDoc capture (works with vkd3d-proton) or reverse-engineer the exe (IDA/Ghidra, Cheat Engine; the Injectable Generic Camera System already has Control camera tables) to locate the world-to-view matrix in the engine's per-view constant buffer, or the CPU-side camera struct before upload. (3) Per eye, offset the camera by ±IPD/2 along its right vector and apply an asymmetric (off-axis) projection, so it converges on a virtual screen plane. That is the right model for a "giant fixed TV", not a toed-in camera. (4) AER: alternate the offset each frame and keep the last image per eye. Synchronous: trigger a second scene render per frame, which requires calling the engine's own render function twice (REFramework-style) and doubles GPU cost. (5) Fix screen-space effects (SSR, SSAO, TAA/FSR history, motion vectors), which break or ghost under alternating cameras. Upscalers need per-eye history or jitter reset. (6) Output: write the two eye images side by side into a swapchain-sized SBS texture (no SteamVR needed), or submit to OpenXR/VRto3D.
- **Synchronous stereo on the 8060S** is only plausible for Control in DX11 (geo-11 already does it). For AW2 and Spider-Man 2, doubling the GPU cost would drop them below 30 fps, so AER is the only realistic DIY mode.
- **At the DXVK/vkd3d-proton layer**, the translation layer would have to identify which constant buffer upload holds the view-projection (heuristic matching per game), duplicate the frame's command lists with patched matrices, and handle bindless descriptor heaps (DX12 titles like AW2/SM2 are heavily bindless). It is feasible for one game with a hard-coded signature, but fragile, and it gains nothing over an in-process hook, which works the same under Proton and Windows. A Vulkan-layer approach is worth considering only for packing SBS output or presenting it.
- Effort: Control would be adopt-and-glue (days). Spider-Man 2 is adopt (R.E.A.L. VR) plus a Proton/OpenXR bridge (unknown, possibly days to weeks). AW2 DIY would be a multi-week reverse-engineering project unless the free NoMoreFlat build turns up.

### Gaps
- No public documentation found of Northlight or Insomniac constant-buffer layouts. That would come from RenderDoc captures on the Z13.
- Unverified whether R.E.A.L. VR or NoMoreFlat (both Windows OpenXR clients) can reach a Linux OpenXR/SteamVR runtime from inside Proton. This decides whether "reuse the baseline mods" is viable on SteamOS at all.
