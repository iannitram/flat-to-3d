**Behaviour**
- **`stop_3d`.** It still runs all 3 commands, in order. If the last one fails and `unit_already_gone(stderr)` holds, it returns `Ok(Stopped)`. Any other failure is still `Err(LinkError)`, so the locked "Access denied" case stays an error.
  - `unit_already_gone` is true for `Unit flat3d-wivrn.service not loaded` or `Unit flat3d-wivrn.service not found`, and for nothing broader. "Failed to connect to bus: No medium found" stays an error.
- **`start_3d_commands_with`.** It builds the same 4 lists as the locked function, with two changes:
  - The server list is `systemd-run --user --collect --unit=flat3d-wivrn flatpak run [<scope.flag()>] --command=wivrn-server io.github.wivrn.wivrn <s.flags…>`.
  - The `am start` list ends with `s.app`.
- **`start_3d_with`.** Same flow as `start_3d` (`link.rs:176-188`), over the `_with` lists.
- **`detect_server`.** It tries `User`, then `System`:
  1. `flatpak info --show-location <flag> io.github.wivrn.wivrn`. A failure (`success == false`) means "not here", so it tries the next scope.
  2. `deploy` = the trimmed stdout. `app_dir` = `deploy` minus its last 3 components (`/<arch>/<branch>/<commit>`). It must end in `app/io.github.wivrn.wivrn`, otherwise it tries the next scope.
  3. `flatpak info <flag> io.github.wivrn.wivrn` → `version_from_info` (the trimmed `Version:` line). A failure here gives `version: None`.
  4. If neither scope matches, it returns `Err("WiVRn server is not installed as a Flatpak (tried --user and --system); fix: flatpak install --user flathub io.github.wivrn.wivrn")`. The fix is the same one WP-29's `wivrn-server` check prints.
- **`detect_quest_app`.** For each id in `QUEST_APPS`, in order, it runs `["adb","-s",serial,"shell","dumpsys","package",id]`. The first output with a trimmed `versionName=` line wins. A successful output with no `versionName=` line (for example `Unable to find package: …`) moves the loop to the next id. An adb failure (`success == false`) returns None at once and tries no further ids. If no candidate matches, the result is None. `AdbRunner` resolves `adb` and leaves an explicit `-s` alone (`tether/adb.rs:191-208`), so a runner with or without a serial both work.
- **Effects.** Detection is read-only. `detect_server` runs only `flatpak info …`, and `detect_quest_app` runs only `adb -s <serial> shell dumpsys package …`. Neither writes a file, starts a unit or changes the headset.
- **Callers.** Other WPs switch the production callers, using exactly these names (§2 "Callers"):
  - WP-10: the tether connect steps (`tether/mod.rs:78` today, `tether.rs` after WP-01) via `Tether::set_wivrn`;
  - WP-09: the service `StartLink` (`watch.rs:264` today, `watch/machine.rs` after WP-01), with `detect_quest_app(r,&serial)`, then `.package`;
  - WP-29: `detect_server`, then `.version`;
  - WP-31: `detect_server(r).map_err(|e| format!("wivrn: {e}"))`.
  - Those edits are outside this WP.
