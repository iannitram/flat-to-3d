- The exit codes are the tool's own (§2: tool exit codes stay per tool): 2 bad args, 3 not Windows, 4 no game found, 5 inject failure. They match the WP-01 stub and §2.
- Every error goes to stderr as one `error_line`. The tokens are `usage`, `not-windows`, `no-game` and `inject`, and every line names its fix.
- `main.rs` does `use flat3d_uevr_inject::{args, ..}` and parses `std::env::args().skip(1)`. It does not declare `mod` lines, so no module is compiled twice.
  - Bad arguments: print `error_line("usage", <e>, USAGE)` to stderr and exit `EXIT_USAGE`.
  - `#[cfg(windows)]`: `flat3d_uevr_inject::win::run(&a)`.
  - `#[cfg(not(windows))]` stub: do `let _ = a;` first, so the unused parsed Args raise no `unused_variables` warning under `-D warnings`. Then print `error_line("not-windows", "Windows only", "let Proton start it through PROTON_REMOTE_DEBUG_CMD (WP-14 debug_cmd)")` and exit `EXIT_NOT_WINDOWS`.
- All Win32 code lives in `win.rs`, behind `#[cfg(windows)]`. `windows-sys` sits under `[target.'cfg(windows)'.dependencies]` (WP-01), so Linux CI clippy never compiles it. `args.rs` and `pick.rs` are `pub` and used by both the tests and main, which leaves no dead_code under `-D warnings` and needs no `allow(dead_code)`.

**Behaviour**
- **`parse`**
  - Flags take their value from the next argument only. `--k=v` is an error.
  - Exactly one of `--exe` or `--pid` is required. `--pid 0` is an error.
  - At least one `--dll` is required.
  - `--delay` and `--wait` must parse as u64.
  - These are errors: a repeated `--exe`, `--pid`, `--delay` or `--wait`; an unknown flag; a missing value.
  - Each `--dll` must be an absolute Windows path: an ASCII letter, then `:\`. Anything else is an Err, Unix paths included, because `LoadLibraryW` with a bare name searches the game's folder. There is no conversion: the value is kept byte for byte.
  - This file is the contract here. `questions.md` entry 31 describes an older draft that kept a `to_win_path` conversion; there is no `to_win_path` in WP-15, and WP-14's `debug_cmd` already sends `Z:\` paths.
- **`choose`**
  - A candidate is a process whose `stem_of(path)` equals `stem`, ignoring ASCII case.
  - A candidate is `preferred` when its path, lowercased and with `/` turned into `\`, contains `\binaries\win64\`. Zero Company has two `SWZeroCompany.exe` (uevr-openxr.md:27).
  - It returns the **last** preferred candidate in list order. With no preferred candidate it returns the last candidate, and with no candidates it returns None.
- **`has_module`** compares basenames, ignoring case.
- **`Waiter::step`** (pure, so the wait logic is tested on Linux):
  - It calls `choose(procs, stem)`.
  - A preferred pick returns `Some(pid)` at once.
  - A non-preferred pick returns `Some(pid)` only when the same pid has come back from `choose` with `preferred == false` for `FALLBACK_AFTER_S` seconds in a row (`now_ms - first_seen_ms >= FALLBACK_AFTER_S * 1000`). Until then it returns None.
  - A different non-preferred pid restarts the timer. None from `choose` clears it.
- **`win::run`**
  - **Wait for the game.** Poll every 500 ms for up to `wait_s`:
    - Take a `CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0)`. A snapshot equal to `INVALID_HANDLE_VALUE` is a failure.
    - Set `entry.dwSize = size_of::<PROCESSENTRY32W>() as u32` before `Process32FirstW`, then walk with `Process32NextW`.
    - Read each full path with `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` and `QueryFullProcessImageNameW(PROCESS_NAME_WIN32)`. A null `OpenProcess` handle (or a failed query) falls back to `szExeFile`.
    - Feed the list to `Waiter::step` with the elapsed milliseconds. Its `Some(pid)` ends the wait.
    - `--pid` skips the wait.
    - If nothing is found, print `error_line("no-game", "no <stem>.exe after <wait_s>s", "start the game from Steam, or raise --wait")` and exit `EXIT_NO_GAME`.
  - **Delay:** sleep `delay_s`.
  - **Module list:** `CreateToolhelp32Snapshot(TH32CS_SNAPMODULE, pid)`. On `ERROR_BAD_LENGTH` (24), retry up to 5 times, 100 ms apart. Set `dwSize = size_of::<MODULEENTRY32W>() as u32` before `Module32FirstW`, then walk with `Module32NextW`.
  - **Inject each dll in order:**
    - Skip a dll that `has_module` shows is already loaded.
    - `OpenProcess(PROCESS_CREATE_THREAD|PROCESS_QUERY_INFORMATION|PROCESS_VM_OPERATION|PROCESS_VM_WRITE|PROCESS_VM_READ)`. A null handle is a failure.
    - `VirtualAllocEx(MEM_COMMIT|MEM_RESERVE, PAGE_READWRITE)` for the path as UTF-16 with a trailing NUL, then `WriteProcessMemory`.
    - Get `LoadLibraryW` with `GetProcAddress(GetModuleHandleW(w!("kernel32.dll")), c"LoadLibraryW".as_ptr().cast())`. The `.cast()` is needed because `PCSTR = *const u8` (windows-sys-0.61.2 core/mod.rs:10; LibraryLoader/mod.rs:33), while `CStr::as_ptr` is `*const c_char`.
    - `GetProcAddress` returns `FARPROC`, an `Option`: `let Some(f) = GetProcAddress(..) else { /* inject failure, exit 5 */ }`.
    - Cast `f` with an annotated `transmute::<unsafe extern "system" fn() -> isize, unsafe extern "system" fn(*mut c_void) -> u32>` (clippy `missing_transmute_annotations`). Pass `Some(start)` as the `LPTHREAD_START_ROUTINE`.
    - `CreateRemoteThread`, then `WaitForSingleObject(h, 60_000) == WAIT_OBJECT_0`, then `VirtualFreeEx(.., 0, MEM_RELEASE)`.
    - Check success with `has_module` on a fresh module list, not with the thread exit code. The exit code holds only the low 32 bits of the HMODULE, which can be 0 for a 4 GiB-aligned base.
    - On failure, print `error_line("inject", "<dll>: GetLastError=<n>", "check that the dll exists; flat3d-inject setup fetch uevr fetches UEVR")` and exit `EXIT_INJECT`.
  - Exit 0 after the last dll. Proton kills the injector when the game exits anyway (uevr-openxr.md:129-133).
  - An RAII `struct Handle(HANDLE)` closes handles. Its Drop calls `CloseHandle`, and skips null and `INVALID_HANDLE_VALUE`.
- **`tools/build-win.sh [--debug] [--install] [--dry-run] [--fetch-sdk]`** (`set -euo pipefail`, shellcheck clean)
  - It starts with `repo=$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd); cd "$repo"`.
  - `XWIN=${FLAT3D_XWIN_DIR:-$HOME/.local/share/flat-to-3d/xwin}`. It needs `$XWIN/crt/lib/x86_64`, `$XWIN/sdk/lib/um/x86_64` (kernel32.lib) and `$XWIN/sdk/lib/ucrt/x86_64`.
    - If any are missing, print the fix, `$HOME/.local/share/flat-to-3d/tools/xwin --accept-license splat --output "$XWIN"` (or `tools/build-win.sh --fetch-sdk`), and exit 3.
    - `--fetch-sdk` runs that command. It is the script's only network step. Running it is the owner accepting the SDK licence (Q2), so it is owner-only: the agent never runs it.
  - If `rustup target list --installed` lacks `x86_64-pc-windows-msvc`, print the fix, `rustup target add x86_64-pc-windows-msvc`, and exit 3. The script never runs `rustup target add` itself.
  - `RUSTFLAGS="-Clinker=rust-lld -Ctarget-feature=+crt-static -Lnative=$XWIN/crt/lib/x86_64 -Lnative=$XWIN/sdk/lib/um/x86_64 -Lnative=$XWIN/sdk/lib/ucrt/x86_64"`. With `--target`, RUSTFLAGS reaches target artifacts only.
  - `CARGO_TARGET_DIR=${CARGO_TARGET_DIR:-$repo/target/win}`, so a RUSTFLAGS change doesn't rebuild the host target.
  - `cargo build --locked --release -p flat3d-uevr-inject --target x86_64-pc-windows-msvc`.
  - Copy `$CARGO_TARGET_DIR/x86_64-pc-windows-msvc/release/flat3d-uevr-inject.exe` to `dist/tools/flat3d-uevr-inject.exe`. Check that its first 2 bytes are `MZ`, then print the `sha256sum`.
  - `--install` runs `install -Dm755` to `${XDG_DATA_HOME:-$HOME/.local/share}/flat3d/bin/flat3d-uevr-inject.exe`. This is the same file as WP-14's `injector_path(p)` (`p.data/bin/flat3d-uevr-inject.exe`) and WP-29's `injector` doctor check, whose fix is `tools/build-win.sh --install`.
  - `--dry-run` still makes the SDK and target checks above (they only read, and exit 3 as usual). Then it prints the env (`XWIN`, `RUSTFLAGS`, `CARGO_TARGET_DIR`) and the cargo, copy and (with `--install`) install argv, one per line, runs none of them, and exits 0.
  - `+crt-static` is not proved until the first real link. If the link fails with it, drop it (Wine's builtin vcruntime140 covers that case) and say so under Not verified.

**Argv contract with WP-14.** WP-14's `debug_cmd` text is the one argv contract; WP-15 does not restate it. In short: `cmd[0]` is the absolute Unix path of the exe (Proton runs it), the stem and each `--dll` value are single-quoted, and every `--dll` is a full `Z:\` path. Proton splits the string with POSIX `shlex.split`, which keeps backslashes literal inside `'…'`. v1's `--uevr-dir` is not used. WP-15 converts no paths.
