**Behaviour:**
- **`inject(p, appid, r)`**, in this order. Nothing is written before step 5.
  1. `catalog::find_recipe(&p.recipe_dirs, appid)`. `Ok(None)` → `not-found` "no recipe for {appid}". `Err` → `bad-recipe`. Parse the text with `recipes::parse_recipe(appid, &text)`. Err → `bad-recipe`.
  2. `check_injectable(&recipe)`. Err(text) → `refused` with that text.
  3. `settings = recipes::route_settings(&text)`, then `recipes::check_route_settings(&recipe.route, &settings)`. Err → `bad-recipe`.
  4. Find the game: `steam::installed_games(&p.home.join(steam::DEFAULT_STEAM_ROOT))`, then the entry with this `appid`. Missing → `not-found` "{appid} is not installed". An io Err → `io`.
  5. Run the private reuse check (ensure_applied step 1) to pick the summary, then call `ensure_applied(&game, &recipe, &settings, p, r)` and map its String error (see "Error mapping").
  6. Return `InjectResult{appid, route:<"uevr"|"geo11">, launched:false, summary}`. The summary is "{name}: already set up" when the reuse check passed, else "{name}: set up for {route}".
  - Routes never write Steam launch options and never start the game (#27).
  - The locked `cli_json` runs `inject 5 --json`. Appid 5 has no recipe, so it returns `not-found` with no writes and no runner calls.
- **`ensure_applied(game, recipe, settings, p, r)`:**
  1. **Reuse:** the record (`undo::record_path(&p.data, appid)`) and the env file `p.env_file(appid)` both exist, every path in the record's `created` exists (this includes the route's `.flat3d-applied` marker), and `parse_env_file` gives the same route and settings → return its `RouteEnv`. No fetch, no writes, no runner calls.
  2. **Stale:** a record exists but step 1 failed → `undo::undo_game(&p.data, appid)`, then go on to step 3.
  3. **Route:** `route_of(&recipe.route)`. Port → Err `"not-built: port route: #27b (WP-27)"`. The `(WP-27)` tag is needed because WP-01's `tests/architecture.rs` fails on any `"not-built: …"` literal without a `(WP-xx)` tag (Craft review A10). NoRoute → Err `"refused: …"` with the `check_injectable` text.
  4. **Pins.** The `uevr-profile` and `geo11-fix` values are pin keys (§2 `check_route_settings`, WP-26).
     - Uevr: `uevr`, plus the `uevr-profile` value when the recipe sets it.
     - Geo11: `geo11`, plus the `geo11-fix` value.
     - For each key: `let pin = fetch::pin(key)`, then `fetch::fetch(&pin, p, r)`. `fetch` returns at once, with no commands, when `fetch::is_fetched(&pin, p)` is true, and it unpacks archives itself. There is no separate unpack or sentinel step here, and WP-27 never rebuilds the cache path or reads the marker itself.
     - `apply_with` does not copy the fetched UEVR profile into the prefix yet. That is a WP-14 follow-up.
  5. **Apply:**
     - Uevr: `let (applied, env) = uevr::apply_with(game, settings, p)?` (WP-14). The DLL dir is `uevr::uevr_dir(p)`, which equals `fetch::cache_dir` of the `uevr` pin.
     - Geo11: `geo11::apply(&p.cache(), &game.install_dir, game.appid, settings, &p.viewer_bin())` (WP-16). Callers pass `p.viewer_bin()` (§2), so a missing viewer comes back as a `not-found: …` Err and never falls back to flat. Its `RouteEnv.sidecar` comes from WP-16's `ViewerSpec::to_args()` and is not built here. WP-31 appends `--until-pid`.
     - The String from either apply passes through unchanged. WP-14 and WP-16 own its `<code>: ` prefix.
  6. `undo::save_record(&p.data, &applied.record)`. `launch_options_before` is `""` (OD5), already set by WP-14 and WP-16.
  7. Create the parent dir of `p.env_file(appid)`, then `fsx::write_atomic(&p.env_file(appid), env_file_text(route, settings, &env).as_bytes())`.
  - If step 6 or 7 fails: run `undo::put_back(&applied.record)`, remove the record file if step 6 wrote it, and return Err `"io: …"` with the cause.
  - The wrapper (WP-31) plays flat on Err.
- **Env file format** (`env_file_text` / `parse_env_file` round-trip):
  - Line 1 is `flat3d-env 1`. Then `route\t<uevr|geo11>`; one `setting\tK\tV` per setting, in BTreeMap order; one `set\tK\tV` per env pair, in order; one `unset\tK` each; `sidecar\targ\targ…` only when `Some`.
  - Every field goes through undo's `escape` (tab, newline, backslash). An unknown first line or tag → Err.
- **`save_record`:** create `<data>/undo/`. If `record_path` exists → `refused` "an undo record for {appid} already exists; run flat3d-inject undo {appid} first". Else `fsx::write_atomic(path, rec.to_text())`. fs errors → `io`.
- **`put_back`:** runs the file steps of `undo_actions(rec)` the way `undo_game` does (remove created files, copy backups back and remove them), but never returns early. Each step adds one line: "removed …", "restored …", or "failed …: <err>". It does not touch the record file. `undo_game` stays as it is.
- **cli `inject <appid> [--json]`** (`cli/inject.rs`): match `Command::Inject{appid}`, call `injectors::inject(ctx.paths, appid, ctx.runner)`, and return `serde_json::to_value(result)`. A serde error → `io`. Any other variant → `usage`. Argv errors never reach here: the locked parser returns `INJECT_USAGE` (exit 2).
- **cli `undo <appid> [--json]`** (`cli/undo.rs`): WP-01's moved body calls `undo_game(&ctx.paths.data, appid)`. Usage errors exit 2 with the private `UNDO_USAGE` text (cli.rs:53). Other errors exit 1 (`exit_code`, cli.rs:93).
- **cli `setup fetch <key> [--json]`** (`cli/setup_fetch.rs`):
  - `fetch::pin(key)`, then note whether `fetch::is_fetched(&pin, p)`, then `fetch::fetch(&pin, p, r)`. The pins come from the compile-time `fetch::PINS` (`packaging/pins`, WP-02), not from `p.pins()`.
  - Ok → `SetupReport{steps:[<"cached {dir}" | "fetched {dir}">], summary:"{key} {version} is ready in {dir}"}`.
  - Errors go through WP-13's `From<FetchError> for ApiError`, so an unknown key is `not-found`.
  - The parser (WP-01) gives `usage` for `setup fetch` with no key. That case is tested in WP-29, not here.
- **Error mapping:**
  - `setup_fetch` uses WP-13's `From<FetchError> for ApiError`, the only fetch→ApiError mapping (§2): `UnknownKey` → `not-found`; `TbdAtPin`, `Manual`, `BadPin`, `Scheme` → `refused`; `Command`, `SizeMismatch`, `ShaMismatch` → `command-failed`; `Io` → `io`. The message is `e.to_string()`, which names the fix where WP-13 gives one (`run packaging/pin.sh <key>`, `--check`, or the manual page).
  - Inside `ensure_applied`, a FetchError becomes `format!("{}: {}", a.code, a.message)` with `a = ApiError::from(e)`. An `undo_game` ApiError becomes the same form.
  - Every String `ensure_applied` returns starts with a code from `ERROR_CODES` (api.rs:77) and `": "`. `inject` splits on that prefix into `ApiError{code, message}`. If a String has no such prefix, `inject` returns code `command-failed` with the whole String as the message. The codes stay the locked 8 (ruling D6).
  - A missing game or recipe → `not-found`.
  - Where one command fixes an error, the message names it, in line with `api::error_help` (ruling D2): `flat3d-inject undo <appid>`, `flat3d-inject setup fetch <key>`, `packaging/pin.sh <key>`.
  - Success exits 0 for all three commands. `cli::ok_exit` changes only doctor.

**Effects** (Craft review A9; the `inject`, `undo` and `setup fetch` rows of WP-01's `cli::COMMANDS` registry must declare these, ruling D2):
- `inject`: WritesFiles and RunsCommands. It writes only the undo record under `p.data/undo/`, the env file `p.env_file(appid)`, the fetch cache under `p.cache()`, and the route's own files (the UEVR profile dir, or the Geo-11 files in the game's exe dir). Its only argv are fetch's (`curl`, `sha256sum`, `bsdtar`), and none when every pin is fetched. It never writes `localconfig.vdf` or any Steam launch option, and never starts the game.
- `undo`: WritesFiles only. It puts back the record's files and deletes the record. It runs nothing.
- `setup fetch`: WritesFiles and RunsCommands, inside `p.cache()` only.
- WP-27 does not edit `cli.rs`. If a registry row disagrees with this list, the worker reports it instead of editing it.
