**DTO shapes** (WP-01 `api.rs`; WP-21 `decky/src/types.ts` mirrors them):
- `DoctorCheck{name:String, ok:bool, detail:String, fix:String}`, where `fix` is `""` when ok;
- `DoctorReport{ok:bool, checks:Vec<DoctorCheck>}`;
- `SetupReport{steps:Vec<String>, summary:String}`;
- `LaunchText{options:String}`.

**Pins source for the `pins` check:** `fs::read_to_string(p.pins())` when that file exists, else `fetch::PINS`, then `fetch::parse_pins`. No WP writes `p.pins()` today, so in production this is the compiled table that `fetch::pin` and `setup_fetch` read. The tests seed `p.pins()` to control the check.

**Behaviour:** `cli::doctor::run` gets `serial = adb_serial(ctx.runner)` and calls `doctor(ctx.paths, ctx.runner, serial.as_deref())`. It returns `serde_json::to_value(report)`. `doctor` runs these checks in this order. Each check is a `DoctorCheck`, and the report's `ok` is the AND of all of them. Every fix is a command the user can run, except the version-mismatch fix in check 2.
1. **`wivrn-server`:** `detect_server(r)`. Ok → the detail is `<app_dir>` plus ` <version>` when known. Err → red, and the detail is the message. Fix: `flatpak install --user flathub io.github.wivrn.wivrn` (the same fix WP-12's `detect_server` error names).
2. **`quest-app`:** with no serial, ok:true and detail `SKIP_NO_HEADSET`, and no `dumpsys` runs. Otherwise `detect_quest_app(r, serial)`:
   - None → red, fix `flat3d-inject setup install-apps`;
   - Some(app) → the detail is `<package> <version>`. When the server version (check 1) and `app.version` are both known and `!versions_match(server, app)`, it is red, with detail `server <s>, headset <a>` and fix `update the WiVRn app on the headset to version <s>`. No command fixes a mismatch yet; a follow-up adds one (questions.md 54). The server pin is 26.9.
3. **`adb`:** `running` = `["ss","-tlnp"]` through the runner, then `listener_pid(stdout, 5037)` (a private const), then `fs::read_link(proc_exe_path(pid))`, as watch.rs:845-851 does today. `bundled` = `bundled_adb(home)` only if that file exists. Then `choose_adb(running, bundled)`. The detail is the source (`running`, `bundled` or `missing`). It is red only on `Missing`, with fix `flat3d-inject install` (it copies the bundled adb into `tools_dir`).
4. **`gnirehtet`:** both `relay_path(home)` and `apk_path(home)` exist. These are the `tools_dir` copies that WP-20's install makes, and `apk_path` is the one path WP-10's connect installs from, so doctor checks the same APK that connect uses. Fix: `flat3d-inject install`.
5. **`link-service`:** `["systemctl","--user","is-active",UNIT_NAME]`. Ok when the trimmed stdout is `active`. Fix: `systemctl --user enable --now flat3d-link.service`.
6. **`wrapper`:** `p.wrapper_bin()` exists and has a `0o111` mode bit. Fix: `flat3d-inject install`.
7. **`steam`:** `{home}/{DEFAULT_STEAM_ROOT}/steamapps/libraryfolders.vdf` exists. Fix: `steam` (start Steam once, so it writes the file).
8. **`pins`:** no pin's `sha256` equals `fetch::TBD` (`TBD-at-pin`). The detail lists those keys, comma-separated, in BTreeMap order. Fix: `packaging/pin.sh <key>` (the first key).
9. **`injector`:** `p.data.join("bin/flat3d-uevr-inject.exe")` exists. This is WP-14's `injector_path(p)` and the target of WP-15's `--install`. Fix: `tools/build-win.sh --install`.

Doctor never writes anything and never fails as a whole: each check catches its own error into `detail`.

**Effects** (they must stay true to the `cli::COMMANDS` rows, §2):
- `doctor`: probes only. The only argv it runs start with `["adb","devices"]`, `["adb","-s",<serial>,"shell","dumpsys","package"]`, `["flatpak","info"]`, `["ss","-tlnp"]` or `["systemctl","--user","is-active"]`. It writes no file.
- `setup packages`: probes only (`adb shell pm list packages`).
- `setup launch-env`: with an appid it runs nothing; with none, only `flatpak info …` (through `detect_server`). It writes no file.
- `setup install-apps`: runs commands, and writes the fetch cache through `setup_fetch`.

Setup commands (`cli::setup::run`):
- **`setup packages`:** `packages_command()` → stdout → `parse_packages`. It returns `json!({"wivrn":p.wivrn,"gnirehtet":p.gnirehtet,"missing":missing(&p)})`. `Packages` has no `Serialize` (setup.rs:17), and crate-root `setup.rs` is not in this WP's files, so the JSON is built with `json!`. WP-05 and WP-33 read this exact shape. A runner failure (`success==false`) is `command-failed` with the stderr.
- **`setup install-apps`:** runs `packages` first. Then, for each missing name in order:
  - `WiVRn` → key `wivrn-apk`; the APK is the single `*.apk` file directly inside `fetch::cache_dir(&fetch::pin(key)?, p)`;
  - `gnirehtet` → key `gnirehtet`; the APK is `cache_dir(pin)/gnirehtet-rust-linux64/gnirehtet.apk`. There is no `gnirehtet-apk` pin. WP-13 unpacks with `bsdtar -xf`, which keeps the zip's top folder `gnirehtet-rust-linux64/`.
  - It calls `setup_fetch(key, p, r)?`, which runs no command when the pin's `.flat3d-fetch` marker is in place. Then it runs `["adb","install","-r",<apk>]`. A failure is `command-failed` with the last stderr line.
  - After the installs it runs `packages` again. A name that is still missing is `command-failed`: `still missing after install: <names>`.
  - Each fetch and install adds one line to `steps`. The summary is `installed WiVRn, gnirehtet` (the names done). When nothing is missing, steps is empty, the summary is `nothing to install`, and `packages` runs only once.
- **`setup launch-env`** (returns `LaunchText`):
  - With no appid: `detect_server(r)` gives `dirs`; an `Err(msg)` is `not-found` with that message, which names the flatpak fix. `options` = `PRESSURE_VESSEL_IMPORT_OPENXR_1_RUNTIMES=1 PRESSURE_VESSEL_FILESYSTEMS_RW=<dirs.app_dir> STEAM_COMPAT_LAUNCHER_SERVICE=proton %command%`. These are the same 3 pairs as `exec_spec` (wrapper.rs:238-247). The folder comes from `detect_server`, so user and system installs both work. WP-24 step0 uses this form.
  - With an appid: `options` = `"<p.wrapper_bin() absolute> %command%"`.
- **`setup fetch <key>`:** `serde_json::to_value(setup_fetch(key, ctx.paths, ctx.runner)?)`.
